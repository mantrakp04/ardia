@@ overview
Halyard is a hosted event-streaming API. You publish events to **streams** over HTTPS, and your services read them back through **consumer groups** or receive them as **webhooks**. There are no brokers to run, no partitions to rebalance by hand, and no client library required: every operation is a plain HTTP request.

## What you can build

- Order, payment and inventory pipelines where every service sees every change in order.
- Activity feeds and audit trails that you can replay from any point in time.
- Fan-out to partners over signed webhooks, with automatic retries.

## How the docs are organized

- **Get started** walks you from an API key to your first published event in about five minutes.
- **Guides** cover producing, consuming and webhooks in depth.
- **Platform** documents plans, limits, security and compliance.
- **API reference** lists every endpoint with its parameters and errors.

> **Note:** These pages document API v3, the current version. If you still call `/v2/` endpoints, switch the version in the header to read the v2 docs, and plan your move with [Migrating from v2](/v3/resources/migrating-from-v2).

@@ quickstart
This guide takes you from a new workspace to a published and consumed event.

## 1. Create an API key

In the dashboard, open **Settings › API keys** and choose **Create key**. Give it the `streams:write` and `events:read` scopes. Keys start with `hk_live_` or `hk_sandbox_`.

```bash
export HALYARD_API_KEY=hk_sandbox_51Hf2kQe8...
```

## 2. Create a stream

```bash
curl https://api.halyard.dev/v3/streams \
  -H "Authorization: Bearer $HALYARD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "orders", "partitions": 6}'
```

## 3. Publish an event

```bash
curl https://api.halyard.dev/v3/streams/str_8Kq2vX/events \
  -H "Authorization: Bearer $HALYARD_API_KEY" \
  -d '{"type": "order.created", "key": "cus_311", "data": {"total": 4200}}'
```

## 4. Read it back

Create a consumer group with `start_at: "earliest"` and call [Read events](/v3/reference/read-events). You should see the event you just published, with its partition and offset.

@@ authentication
Every request authenticates with an API key sent as a bearer token.

```http
Authorization: Bearer hk_live_51Hf2kQe8...
```

## Key types

| Prefix | Environment | Notes |
| --- | --- | --- |
| `hk_live_` | Production | Counts toward your plan's usage and rate limits. |
| `hk_sandbox_` | Sandbox | Isolated data, limited to 10 streams and 7 days of retention. |

## Scopes

Keys carry one or more scopes: `streams:read`, `streams:write`, `events:read`, `events:write`, `webhooks:manage` and `audit:read`. A request without the right scope fails with `403 insufficient_scope`.

## Rotating keys

Create the new key, deploy it, then revoke the old one. Revocation takes effect within 30 seconds worldwide. Key creation and revocation are recorded in the [audit log](/v3/platform/audit-logs).

> **Warning:** Never embed live keys in browser or mobile code. Use a server-side proxy or short-lived tokens.

@@ concepts/streams
A **stream** is an append-only log of events. Each stream is split into **partitions**; events with the same partition key always land on the same partition and are read in the order they were written.

## Choosing a partition count

More partitions allow more consumers to read in parallel. A good starting point is one partition per 1,000 events per second at peak, with a minimum of 6. You can raise the count later, but never lower it, and raising it changes which partition a key maps to for new events.

## Retention

Events stay readable for the stream's `retention_hours`. The maximum depends on your plan:

| Plan | Maximum retention |
| --- | --- |
| Starter | 3 days |
| Team | 7 days |
| Business | 30 days |
| Enterprise | 365 days |

@@ concepts/events
An **event** is a JSON object with a `type`, an optional partition `key`, and a `data` payload. Halyard adds an `id`, the `partition`, the `offset` and a `published_at` timestamp.

```json
{
  "id": "evt_01JB9X4T2Q",
  "type": "order.created",
  "key": "cus_311",
  "partition": 7,
  "offset": 88213,
  "published_at": "2026-10-02T17:05:44.120Z",
  "data": {"total": 4200, "currency": "usd"}
}
```

## Naming event types

Use `noun.verb` in the past tense: `order.created`, `invoice.paid`, `shipment.delayed`. Webhook filters and schemas match on the type, so keep it stable.

## Size

An encoded event can be at most 1 MB. See [Size limits and quotas](/v3/platform/quotas) for the full list.

@@ concepts/consumer-groups
A **consumer group** reads a stream on behalf of one application. Halyard assigns each partition to one member of the group at a time, so adding instances spreads the work without duplicating it.

## Membership and rebalancing

Members join implicitly when they call [Read events](/v3/reference/read-events) with a `member_id`. If a member stops polling for 30 seconds, its partitions move to the remaining members. Each rebalance increments the group's `generation`.

## Committing progress

A group remembers one committed offset per partition. Commit after you have finished processing, not before, so that a crash replays work instead of losing it. See [Offsets and replay](/v3/concepts/offsets).

@@ concepts/offsets
Every event has an **offset**: its position in its partition. Offsets increase by one per event and are never reused.

## Committed offsets

A consumer group's committed offset is the last event it has finished processing. You can read the committed offset and the lag for every partition with [Retrieve committed offsets](/v3/reference/get-offsets).

## Replay

To process history again, move the group's commits backwards with `force: true`, or create a new group with `start_at` set to a timestamp. See [Replaying history](/v3/guides/replay).

> **Note:** In v2, offsets were read and committed through `/v2/streams/{stream_id}/offsets`. In v3 they live under the consumer group. The v2 endpoints are deprecated; see [Deprecations and sunsets](/v3/resources/deprecations).

@@ concepts/schemas
Attach a **schema** to a stream to reject malformed events at publish time. Halyard supports JSON Schema draft 2020-12.

## Compatibility modes

| Mode | Allowed changes |
| --- | --- |
| `backward` | Add optional fields, remove fields. Default. |
| `forward` | Add fields, remove optional fields. |
| `full` | Only add or remove optional fields. |
| `none` | Any change. |

## Versions

Each schema update creates a new version. Events record the schema version they were validated against in `schema_version`.

@@ guides/publishing
Publish with [Publish an event](/v3/reference/publish-event) for low volumes, or [Publish a batch](/v3/reference/publish-batch) above a few events per second.

## Partition keys

Pick a key that groups events which must stay in order, such as a customer or order ID. Events without a key are spread round-robin and have no ordering guarantee.

## Acknowledgements

A `200` response means the event is durably stored in three availability zones. If the request times out, retry with the same `idempotency_key` to avoid duplicates.

```js
await halyard.events.publish("str_8Kq2vX", {
  type: "order.created",
  key: order.customerId,
  data: order,
  idempotencyKey: `order-${order.id}`,
});
```

@@ guides/batch-ingest
Batching is the cheapest way to publish at volume: a batch of 500 events counts as one request toward your rate limit.

## Limits

- Up to 500 events per batch.
- The whole request body may be at most 5 MB.
- Each event may still be at most 1 MB.

## Partial failures

A batch is not atomic. The response lists rejected events by `index` with a reason code, and you should retry only those. The Node and Python libraries do this for you.

```json
{"accepted": 498, "rejected": [{"index": 17, "code": "schema_mismatch"}]}
```

@@ guides/idempotency
Send an `idempotency_key` with a publish to make retries safe. If Halyard has already stored an event with the same key on the same stream in the last 24 hours, it returns the original event instead of storing a duplicate.

## Choosing keys

Derive the key from your own data, such as `order-123-created`, rather than generating a random value per attempt. Keys can be up to 255 characters.

> **Note:** Idempotency keys are scoped per stream. The same key on two different streams stores two events.

@@ guides/consuming
Consumers read through a consumer group using long polling.

```python
while True:
    batch = halyard.consumer_groups.read("cg_5TzQ1m", max=100, wait_ms=20000)
    for event in batch.events:
        handle(event)
    halyard.consumer_groups.commit("cg_5TzQ1m", batch.next_offsets)
```

## Throughput

One member can usually process a few thousand events per second. If `lag` keeps growing, add members, up to one per partition.

## Ordering

Events are ordered within a partition only. If you need global ordering, use a single partition, which caps throughput.

@@ guides/replay
Replay lets you reprocess events after a bug fix or backfill a new service.

## Replay an existing group

Commit an older offset with `force: true` on [Commit offsets](/v3/reference/commit-offsets). The group resumes from there on its next read.

## Replay into a new group

Create a group with `start_at` set to an ISO 8601 timestamp. Halyard finds the first event on each partition published at or after that time.

> **Warning:** You can only replay events that are still inside the stream's retention period.

@@ guides/dead-letter
When a webhook delivery or a consumer keeps failing on the same event, set it apart instead of blocking the partition.

## Webhook dead letters

After the final retry, Halyard writes the undelivered event to the endpoint's dead-letter stream, named `<stream>.dlq`, with the last response status and body attached.

## Consumer dead letters

Consumers decide for themselves: publish the event to a `.dlq` stream with your error, then commit past it. Dead-letter streams are ordinary streams and count toward your quotas.

@@ webhooks/overview
Webhooks push events to an HTTPS endpoint you control, so you don't have to run a consumer.

## How delivery works

1. You register an endpoint with [Create a webhook endpoint](/v3/reference/create-webhook).
2. For every matching event, Halyard sends a `POST` with a JSON body and a `Halyard-Signature` header.
3. Your endpoint answers with any `2xx` status within 10 seconds.

## Payload size

Webhook request bodies are capped at **256 KB**. When an event is larger, Halyard sends a thin notification instead, with the event's `id` and a `fetch_url` you can call to retrieve the full event.

## Ordering

Deliveries for the same partition key are sent one at a time, in order. Deliveries for different keys may arrive in parallel.

Next, [verify every request's signature](/v3/webhooks/signatures) before trusting it.

@@ webhooks/signatures
Every webhook request carries a `Halyard-Signature` header so you can confirm it came from Halyard and was not modified.

```http
Halyard-Signature: t=1792345678,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
```

## How the signature is computed

The `v1` value is an **HMAC-SHA256** of the string `{t}.{raw request body}`, keyed with the endpoint's signing secret (it starts with `whsec_`), encoded as lowercase hex.

## Verifying in Node.js

```js
import crypto from "node:crypto";

function verify(header, rawBody, secret) {
  const parts = Object.fromEntries(header.split(",").map((p) => p.split("=")));
  const expected = crypto.createHmac("sha256", secret).update(`${parts.t}.${rawBody}`).digest("hex");
  const fresh = Math.abs(Date.now() / 1000 - Number(parts.t)) < 300;
  return fresh && crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v1));
}
```

## Replay protection

Reject requests whose timestamp `t` is more than five minutes old.

> **Note:** API v2 signed webhooks with HMAC-SHA1 in an `X-Halyard-Signature` header. v3 endpoints only send the `Halyard-Signature` header described here. Asymmetric (Ed25519) signatures are on the roadmap and not yet available.

@@ webhooks/retries
If your endpoint doesn't answer `2xx` within 10 seconds, Halyard retries with exponential backoff.

| Attempt | Delay after previous attempt |
| --- | --- |
| 2 | 30 seconds |
| 3 | 2 minutes |
| 4 | 10 minutes |
| 5 | 1 hour |
| 6 to 12 | 4 hours |

After 12 failed attempts (about 28 hours), the event goes to the endpoint's [dead-letter stream](/v3/guides/dead-letter). An endpoint that fails every delivery for 3 days is disabled and the workspace owners are emailed.

## Redelivery

You can redeliver any event from the last 30 days from the dashboard's **Webhooks › Deliveries** view.

@@ webhooks/local-development
Use the Halyard CLI to forward webhooks to a server on your machine.

```bash
brew install halyard-dev/tap/halyard
halyard login
halyard listen --stream orders --forward-to http://localhost:3000/hooks
```

The CLI prints a temporary signing secret. Use it in your local verification code; it changes every time you run `listen`.

@@ guides/pagination
List endpoints return results in pages using an opaque cursor.

```json
{"data": [...], "next_cursor": "c_Mjk0MQ"}
```

Pass `next_cursor` as `cursor` to get the next page. When `next_cursor` is `null`, there are no more results. Cursors expire after 24 hours.

## Page size

Use `limit` to set the page size, from 1 to 100. The default is 20.

> **Note:** v2 used `page` and `per_page` parameters. Those are ignored by v3 endpoints.

@@ guides/errors
Errors use conventional HTTP status codes and a JSON body.

```json
{"error": {"code": "rate_limited", "message": "Rate limit exceeded. Retry after 3 seconds.", "request_id": "req_7XcPq2"}}
```

## Retrying

| Status | Retry? |
| --- | --- |
| 400, 401, 403, 404, 409, 422 | No. Fix the request. |
| 413 | No. Make the payload smaller. |
| 429 | Yes, after `Retry-After` seconds. |
| 500, 502, 503 | Yes, with exponential backoff and jitter. |

Always log the `request_id`; support will ask for it.

@@ resources/migrating-from-v2
v3 keeps the same resources as v2 but changes a few shapes. Most integrations migrate in a day.

## What changed

| Area | v2 | v3 |
| --- | --- | --- |
| Base path | `/v2/` | `/v3/` |
| Offsets | `/v2/streams/{stream_id}/offsets?group=` | `/v3/consumer-groups/{group_id}/offsets` |
| Pagination | `page`, `per_page` | `cursor`, `limit` |
| Webhook signature | `X-Halyard-Signature`, HMAC-SHA1 | `Halyard-Signature`, HMAC-SHA256 with timestamp |
| Max event size | 256 KB | 1 MB |
| Errors | `{"message": ...}` | `{"error": {"code", "message", "request_id"}}` |

## Suggested order

1. Upgrade your client library to a v3 release.
2. Move producers first; v2 consumers can read events published through v3.
3. Move consumers, creating v3 consumer groups that start at the v2 group's committed offsets.
4. Rotate webhook endpoints to v3 and update signature verification.

See [Deprecations and sunsets](/v3/resources/deprecations) for the dates.
