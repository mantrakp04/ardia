Admin API reference

The Admin API lets you read and update your store's data from your own scripts and tools. It's organised around REST: predictable resource URLs, JSON request and response bodies, standard HTTP verbs and status codes.

Every timestamp is an ISO 8601 string in your store's time zone, America/New_York, with its UTC offset, for example 2026-09-30T22:30:00-04:00.

Base URL
http://127.0.0.1:8861/v1

Authentication

Authenticate with a personal access token. Find yours in the admin under Settings › Developer. Send it in the Authorization header on every request:

Authorization: Bearer <token>

Tokens carry your account's access, so keep them out of shared code. Requests without a valid token get 401 unauthorized. The API doesn't use cookies or CSRF tokens.

Authenticated request
curl http://127.0.0.1:8861/v1/orders?limit=1 \
  -H "Authorization: Bearer $TOKEN"

Errors

Failed requests return a non-2xx status and an error object with a machine-readable code, a human-readable message and, when one parameter is at fault, param.

StatuscodeMeaning
400bad_requestThe body isn't a JSON object, or a cursor is malformed.
401unauthorizedThe token is missing or invalid.
404not_foundNo order has that id, or the URL doesn't exist.
405method_not_allowedThe endpoint doesn't support that HTTP method.
422validation_failedA parameter is unknown or has an invalid value. Nothing was changed.
429rate_limitedToo many requests. See Rate limits.
Error response
HTTP/1.1 422 Unprocessable Entity

{
  "error": {
    "code": "validation_failed",
    "message": "status must be one of processing, shipped, delivered, archived",
    "param": "status"
  }
}

Rate limits

Each token can make 10 requests per second, with bursts of up to 10. A batch request counts as one request, however many operations it holds.

Over the limit, the API answers 429 rate_limited with a Retry-After header giving the number of seconds to wait. Every response carries X-RateLimit-Limit and X-RateLimit-Remaining.

429 response
HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 0

{
  "error": {
    "code": "rate_limited",
    "message": "Too many requests. Limit is 10 per second; retry after 1 s."
  }
}

Pagination

List endpoints return orders newest first, in pages. Set limit (1 to 100, default 50). When has_more is true, pass the response's next_cursor as cursor, with the same filters, to get the next page. Keep going until has_more is false.

Cursors point after the last order you received, so updating orders while you page through a list doesn't make you skip any.

List response
{
  "object": "list",
  "data": [ { "object": "order", "id": 5981204, ... } ],
  "has_more": true,
  "next_cursor": "YWZ0ZXI6NTk4MTIwNA"
}

GET /v1/orders

Lists orders, newest first. Filters combine with AND.

ParameterDescription
statusOne status, or several separated by commas.
channelOne channel, or several separated by commas.
tagOnly orders with this tag (ignoring case).
qFull-text search over order number, customer name and email, note and tags.
created_at_min, created_at_maxOnly orders placed at or after _min and before _max.
delivered_at_min, delivered_at_maxOnly orders delivered at or after _min and before _max. Orders that haven't been delivered never match.
limitPage size, 1 to 100. Default 50.
cursorThe next_cursor from the previous page.

Time filters take a timestamp or a date. A date means midnight at the start of that day in the store's time zone, so delivered_at_max=2026-09-01 matches orders delivered up to the end of August 31.

Request
curl -G http://127.0.0.1:8861/v1/orders \
  -H "Authorization: Bearer $TOKEN" \
  -d status=shipped \
  -d channel=wholesale \
  -d limit=100

GET /v1/orders/{id}

Retrieves one order by its id.

Request
curl http://127.0.0.1:8861/v1/orders/5410337 \
  -H "Authorization: Bearer $TOKEN"

PATCH /v1/orders/{id}

Updates an order. Send only the fields you want to change; it returns the updated order.

FieldDescription
tags_addTags to add. The order keeps its other tags; tags it already has are left as they are.
tags_removeTags to remove, ignoring case.
tagsReplaces the whole tag list. Can't be combined with tags_add or tags_remove.
statusprocessing, shipped, delivered or archived. Archiving sets archived_at and keeps the shipping and delivery dates. Moving an order back to processing clears them.

An update is all or nothing: if any field is invalid you get 422 and the order doesn't change.

Request
curl -X PATCH http://127.0.0.1:8861/v1/orders/5410337 \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"tags_add": ["reviewed"], "status": "archived"}'

POST /v1/orders/batch

Applies up to 50 updates in one request. Each operation is an id plus the same fields as Update an order.

Operations are applied in order and independently: one that fails doesn't stop the others. The response has one result per operation, in the same order, each with its own status and either the updated order or an error. Check every result.

Request
curl -X POST http://127.0.0.1:8861/v1/orders/batch \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"operations": [
        {"id": 5410337, "tags_add": ["reviewed"]},
        {"id": 5410498, "status": "shipped"}
      ]}'
Response
{
  "object": "batch",
  "results": [
    { "id": 5410337, "status": 200, "order": { ... } },
    { "id": 5410498, "status": 404, "error": {
        "code": "not_found",
        "message": "No order with id 5410498" } }
  ]
}
