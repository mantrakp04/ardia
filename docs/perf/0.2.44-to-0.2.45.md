# 0.2.44 → 0.2.45 release gate

0.2.45 collects nightlies 1 to 4 and moves the engine from Chromium 156 to 157.0.8103.38 (Helium 0.21.1): lazy profile loading, unread badges, links from pinned tabs and Top Apps in a Peek, WebKit ad blocking, Report a Problem, .crx drops, the page frame slider, auto-hide tabs as a setting and the `ardia tabs`/`groups`/`apply` commands. 0.2.44 is native API 47 and 0.2.45 is 54, so each app ran its own bench bundle, both built from `git archive` (below): `dist/0.2.44/bench/main.jsbundle` from `v0.2.44` and `dist/0.2.45/bench/main.jsbundle` from 4fcccdfb1, not from the working tree, which held other sessions' uncommitted edits. The candidate is CI's signed and notarized RC (build 109, 4fcccdfb1). Measured on 2026-11-09, interleaved, on AC, load average 2 to 5. cpu-cap wasn't running (its log ends on 2026-11-06), so no run was paused. The owner used the Mac during the first round (35 to 81 s of input per idle window) and barely during the later ones.

**Result: passes after a fix.** The first candidate failed on one row: idle CPU at 1 tab separated in three interleaved rounds. The cause was Chrome's TPM latency benchmark, a one-off task whose timing Chromium 157 moved into the bench's idle window (below). 71c273239 compiles it out on the Mac (`chromium-tpm-metrics-off.patch`), and the final candidate (CI build of 447d63054) passes that row (below, "After the fix").

## Ratchet

The first RC went over on many counts. Bisecting the nightlies' own bundles found six regressions in app code, all fixed in 7675e1c70: PeekMark subscribed every tab icon to the whole browser store (switchTabs.subNotified 29602 → 24252), UnreadBadge started a native spring on every mount with no badge (launch.tasks.callback 217 → 28), TabRow kept an extra View under the Back to Pinned URL wrapper (launch.mounts 6852 → 6675, hover.renders 768 → 720), the page frame slider subscribed about 25 components to the store for one setting, the popover Escape capture listened with no popover open, and the live engine added a second store listener next to an existing one. 4fcccdfb1 raised 18 ceilings by reason, each counted to the feature that ships it: unread badges and the Peek mark in every tab icon, shared Top Apps paging, .crx drops, Report a Problem, auto-hide tabs, hover cards, the command-line control pill, the page frame setting, three browser-store listeners (lazy profiles, Peek's landing check, crash-context reset), the popover Escape capture on the pages store, and telemetry's install and session ids (two more writes on the one-tab launch). None of it comes from Chromium 157: every count is already in nightly.4 on 156, and from nightly.4 to the RC no gated count went up. The final build passes: `ratchet: ok`, 0 over, 69 below.

| `--only idle --runs 1 --idle 150` | 0 / 23 | 0.67 → 1.16 % | 1.43 → 1.65 % |

The cause is Chrome's TPM latency measurement, not a steady cost. `sample` of every thread over the window (40 s from 42 s after launch) puts the extra time on one ThreadPoolBackgroundWorker: about 440 busy samples against 39 on 0.2.44, 0.6 s of thread CPU. It runs `crypto::MaybeMeasureTpmOperations` → `MeasureTpmOperationsInternal` four times, each almost all in `UnexportableKeyProviderApple::DeleteWrappedKeysSlowly` → `FindUnexportableKeys` → `SecItemCopyMatching`, which makes a Secure Enclave key object for every matching keychain item over synchronous XPC to ctkd and securityd. 0.2.44 does the same work (same functions, about 350 samples per pass), but at startup: it shows up in the bench's short seeding launch and nowhere in the measured launch's 5 to 205 s. On 157 it runs 30 to 90 s after launch, inside the 1-tab idle window, in every run sampled (3 of 3). It is done by the 20-tab window, where both apps are the same, and over a 150 s window the difference falls to half. So the same one-off work (about 0.6 s of CPU in the browser process per launch, plus securityd's and ctkd's, which the tree doesn't count) moved from launch to a minute after it. It's metrics-only work: Helium sends no UMA, so the measurement goes nowhere, and it creates and deletes Secure Enclave keys in the login keychain on every launch. Turning the measurement off in the engine would remove it on both versions. Its cost grows with the matching keys in the keychain, and this Mac has run many test instances, so a user's pass is probably shorter.

**Memory fell by a quarter** at every tab count, from the engine: the same number of processes (7, 16, 26), each child smaller. At 1 tab the renderer went 64 → 38 MB, uBlock Origin's extension process 124 → 71 MB, and the network and storage utilities 24 → 11 and 19 → 6 MB; at 20 tabs the renderers 709 → 443 MB. The browser process is the same (162–165 MB at 20 tabs). App code doesn't run in those processes, so this is Chromium 157 and Helium 0.21.1. Lazy profile loading isn't in it: the bench session has one profile.

## The bench bundles

Run from the checkout once per app: `REV=v0.2.44 S=~/ardia-scratch/perfgate-0245/bundle-0244`, then `REV=4fcccdfb1 S=~/ardia-scratch/perfgate-0245/bundle-0245`. Each `out/main.jsbundle` and `out/assets` went to `dist/<v>/bench/`.

```
REPO=$PWD; mkdir -p $S/src $S/out
git archive $REV | tar -x -C $S/src
for d in node_modules apps/browser/node_modules packages/{core,shaders,import,ardiacore}/node_modules; do cp -Rc "$d" "$S/src/$d"; done
R=$S/src; N=$(command -v node); cd $R/apps/browser
"$N" "$R/node_modules/react-native-macos/scripts/bundle.js" bundle --entry-file scripts/perf/bench-entry.js --platform macos --dev false --minify false --bundle-output "$S/out/bench.js" --assets-dest "$S/out/assets" --config-cmd "'$N' '$R/node_modules/react-native-macos/cli.js' config"
"$REPO/apps/browser/macos/Pods/hermes-engine/destroot/bin/hermesc" -emit-binary -O -out "$S/out/main.jsbundle" "$S/out/bench.js"
```
